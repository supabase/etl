## Independent benchmark

Hardbyte's independent CDC benchmarks compare six configurations across
steady-state delivery, mixed-speed consumers, and consumer outages. The table
summarizes latency, runtime memory, and source WAL retention for all six
configurations, in alphabetical order. **Bold marks the lowest reported value in each
column, including ties at the published precision.**

| CDC configuration | Fast-consumer tail latency | Fast-consumer memory | Mixed-speed tail latency | Source slot WAL during outage |
| --- | ---: | ---: | ---: | ---: |
| Debezium + Kafka | 961 ms | 1,385.4 MB | 1,074 ms | **11.0 MB** |
| Debezium Server | 848 ms | 1,629.3 MB | 1,181 ms | 57.3 MB |
| Raw pgoutput (SQL polling) | 70 ms | 59.7 MB | 267 ms | 56.6 MB |
| Sequin | 33 ms | 595.2 MB | **33 ms** | 642.0 MB |
| Sequin with message grouping | 33 ms | 624.3 MB | **33 ms** | 679.9 MB |
| Supabase ETL | **26 ms** | **13.0 MB** | 273 ms | 57.2 MB |

### Workloads and metrics

Each column compares tools within its own scenario; the columns do not describe
one combined run. These fixed-rate tests do not measure maximum throughput.

- **Fast consumers:** [steady-state results](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-long/REPORT.md#fanout_steady)
  at 200 source changes/s with four fast HTTP consumers on PostgreSQL 18.3.
  Tail latency is the worst consumer's median rolling 30-second p99.
- **Memory:** the largest sum of sampled process or container peaks within
  any phase of the fast-consumer run, in decimal MB. Measurements use native
  process RSS or Docker memory; component peaks need not coincide. They include
  measured sidecars and broker components, but exclude source Postgres and the
  harness.
- **Mixed-speed consumers:** [steady-state results](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-hetero/REPORT.md#fanout_steady)
  at 150 source changes/s with one fast, two normal, and one slow HTTP consumer,
  using the same tail-latency statistic.
- **Source slot WAL:** the largest per-slot retained-WAL peak during the
  [consumer outage](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-long/REPORT.md#dead_consumer),
  at 200 source changes/s with four fast consumers, one of which stops accepting
  changes. This is not a sum across slots or a measure of total backlog storage. Kafka retained
  less source WAL while accumulating a separate backlog in the broker.

The full reports contain delivery rates, recovery behavior, and verifier
results; the author also published [cross-table transaction results](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-ledger/REPORT.md).

### Tested configurations

ETL ran four pipelines in one Rust process, using a
[custom `HttpDestination`](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/etl-cdc-bench/src/main.rs)
and **`MemoryStore` for in-memory state and checkpoints**. This avoids the
database round trips and persistent checkpoint writes of `PostgresStore`;
built-in warehouse destinations were not tested.

The adapter [pinned ETL](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/etl-cdc-bench/Cargo.toml)
to [commit `d206d66e`](https://github.com/supabase/etl/commit/d206d66eabaa3cfd15872eba761c5131e22a7f75),
with a 20 ms batch-fill timeout. Debezium Server used
[3.1.3.Final](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-long/cdc-20260722T021356Z-dfe217/manifest.json)
across four JVMs in the fast-consumer and outage runs. The mixed-speed run used
[Debezium Server 3.6.0.Final](https://github.com/hardbyte/postgresql-job-queue-benchmarking/blob/7b2919a0fd668a84efc68500ac94cfbfbd3b7356/results/cdc-sweep-hetero/cdc-20260722T203235Z-6b6ffb/manifest.json).
These single-run results have no confidence intervals. They describe the
tested versions and implementations, and do not measure
subsequent improvements to ETL.
