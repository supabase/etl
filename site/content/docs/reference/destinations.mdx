Supabase ETL ships official destination implementations in the
`etl-destinations` crate. Enable only the destination feature you need when
embedding ETL or building the standalone replicator. **ClickHouse is the
easiest destination to start with locally:** `cargo x init` starts it, and
`cargo x setup replicator` configures it by default. **BigQuery is the most
mature cloud destination.**

| Feature      | Destination     | Status        | Guidance                                  |
| ------------ | --------------- | ------------- | ----------------------------------------- |
| `clickhouse` | ClickHouse      | Public alpha  | Recommended local getting-started path    |
| `bigquery`   | Google BigQuery | Public alpha  | Most mature cloud destination             |
| `ducklake`   | DuckLake        | Public alpha  | Evaluate for your workload                |
| `snowflake`  | Snowflake       | Public alpha  | Evaluate for your workload                |
| `iceberg`    | Apache Iceberg  | Deprecated    | Do not use for new deployments            |

## Status definitions

- **Public alpha:** The managed service is in public alpha. Features and
  behavior may change. Local and self-hosted use of the open-source destinations
  is unrestricted. Review limitations and test recovery and schema changes
  against your workload before production use.
- **Deprecated:** Retained for compatibility but no longer recommended for new
  deployments. Plan to move away from it.

## Row value handling

ETL validates structural prerequisites such as primary keys, replica identity,
column mappings, and schema transitions. It does not pre-validate each row value
against destination-specific domains. When ETL can represent a value in the
destination request or wire format, it sends that value and relies on the
destination's native coercion, rounding, canonicalization, and rejection
behavior. These semantics apply consistently to initial copy, inserts, and
updates.

For row values, ETL returns a local encoding error when it cannot construct a
faithful wire representation. Known destination differences do not add per-cell runtime
validation. Test destination-specific value semantics that matter to your
workload.

## Publication column additions

An existing column newly exposed by a publication is added as nullable so old
destination rows remain `NULL`. Defaults and array handling differ by
destination. See [Publication column
changes](/explanation/schema-changes/#publication-column-changes) for the
complete policy.

## Destination ownership

ETL assumes exclusive ownership of every data-bearing table it creates.
Destinations name their objects deterministically from the source table name,
so destination metadata records only schema snapshots and whether initial
setup or a schema change completed. ETL owns the destination names derived
from every snapshot that metadata records: the current snapshot, and while a
schema change is `Applying`, also the previous one. Destinations may cache the
completed state. Once metadata is `Applied`, ETL does not recreate a missing
table or repair external schema changes during ordinary writes or restart.
Such changes are unsupported and typically cause the destination operation to
fail.

Resetting a table for a fresh copy removes the objects under every owned name
that exists, then creates the table again. The active destinations never adopt
an existing object during fresh creation: if a name is still occupied, they
fail and ask you to drop that object. During `Applying`, every object reachable
through either recorded snapshot's destination name is treated as owned for
reset, including an object now used by another replicated table. Reset
deliberately cleans up both endpoints of this intermediate state; it does not
infer which rename steps completed or reconstruct ownership through a sequence
of renames.

ETL may rebuild ephemeral client state and destination-specific derived
objects, such as Snowflake streaming channels. Direct destination
truncation is also outside ETL's lifecycle: later behavior depends on the
destination's offset and write semantics, and previously replicated rows are
not restored automatically.

### Upgrading existing pipelines

Existing pipelines that follow the earlier release's supported lifecycle can
resume with the same configuration, source replication slots, destination
objects, and persisted checkpoints. No fresh copy is required. BigQuery views
continue selecting their existing physical tables, and DuckLake preserves the
spelling of existing replay-state keys, including mixed-case source names.
CDC ordering and replay formats are unchanged.

Stop each pipeline and wait for its old process to finish draining and exit
before starting the new image. Other pipelines can continue using earlier
images: the Postgres metadata schema is unchanged. Avoid overlapping old and
new workers for the same pipeline, and enable live table renames only after
that pipeline has upgraded.

If a previous BigQuery DDL operation has an unknown outcome, reconcile its job
before restarting or resetting tables. See [query completion and recovery](#query-completion-and-recovery).

The `destination_table_id` column is retained for compatibility and manual
inspection. Every destination metadata write inserts or overwrites it with the
supplied identifier; for BigQuery, this is the physical table ID. Keeping the
column preserves existing information while snapshot-based naming is evaluated.
It is write-only for this version of ETL: startup and metadata loaders never
read it, and it is excluded from the runtime `DestinationTableMetadata` type.
Runtime operations derive names from the recorded snapshots and, for BigQuery,
discover the physical table through the logical view.

The column records only the last identifier supplied by the destination. It can
be stale after interrupted DDL and does not retain both endpoints of a rename
or every physical table created during replacement. It is not proof of
ownership and provides no automatic recovery or rollback guarantees.

Earlier releases did not support live table renames. If a source was renamed
while running an earlier image, check that its recorded snapshots still name
the destination objects before upgrading. The new image does not validate the
fallback identifier. Repair mismatched objects and metadata together, or
coordinate fresh copies for affected source names. A reset derives names from
snapshots and cannot discover an old name absent from those snapshots.

A binary-only rollback is not guaranteed after renames or a BigQuery physical
table swap. Stop the pipeline and verify that destination objects and metadata
are compatible with the earlier image before restarting it. The retained
identifier does not describe both endpoints of an interrupted rename or
resolve an unknown remote DDL outcome.

## BigQuery

<DestinationStatus status="public-alpha" />

This status applies to the managed service, not local or self-hosted use.

BigQuery uses the BigQuery Storage Write API and BigQuery change data capture
to maintain destination tables. Use it when you already have a Google Cloud
project. For a local first pipeline, prefer [ClickHouse](#clickhouse).

### Views and physical tables

Query the logical view for each replicated table. Its name is derived from the
source table name and is the only BigQuery name ETL depends on. The view
selects a physical table that holds the rows; ETL finds that table by reading
the view definition. The physical table ID is still written to
`destination_table_id` in Postgres for compatibility and manual inspection; it
is never used for discovery.

New physical tables are named
`supabase_etl_<pipeline_id>_<table_oid>_<suffix>`, where the suffix is 25
lowercase letters and digits encoding a random UUID. ETL never reuses a deleted
physical name, avoiding stale table and ingestion references while deletion
and creation propagate through BigQuery. Tables created by earlier releases,
named `<view>_<version>` with a numeric or random suffix, keep working: ETL
reads, alters, truncates, and deletes whichever table a view selects. No
migration or recopy is required to upgrade.

Target discovery uses [`tables.get`](https://docs.cloud.google.com/bigquery/docs/reference/rest/v2/tables/get), which returns the logical view's SQL
definition without executing it. ETL accepts a GoogleSQL view selecting all
columns from one fully qualified, backtick-quoted table in the configured
project and dataset. Keyword case, ASCII whitespace, and a trailing semicolon
are accepted. Only the backtick and backslash escapes emitted by ETL are
decoded; other escapes and more complex queries are rejected rather than
interpreted as a different table name. Legacy numeric and random physical
suffixes both use the same view definition shape.

Query-job [`referencedTables`](https://docs.cloud.google.com/bigquery/docs/reference/rest/v2/Job#JobStatistics2) is not used for discovery. It describes a query's
dependencies and requires planning that query against its dependencies.
Reading the stored view definition also works when the physical table is
already missing. During reset, a discovery failure logs a warning and may
leave an orphaned physical table; ETL still removes the owned logical view.
Failure to remove that view prevents the next copy from claiming its name.

BigQuery trusts its per-table applied cache during ordinary writes. A cache
miss loads destination metadata and reads the view definition once. Every batch
must match the cached snapshot ID, replication mask, and logical source name.
The write descriptor is cached separately for that endpoint and copy/CDC mode.

Lifecycle changes serialize per table and invalidate the cache before changing
BigQuery:

- **Initial setup** rejects an occupied view name, records `Creating`, creates
  the physical table and the view, and records `Applied`.
- **Truncate** creates a fresh physical table and atomically replaces the view
  to select it, so readers always see one complete table: the old one before
  the replacement and the new one after. Truncate does not change destination
  metadata. The replaced table is then deleted in the background.
- **Schema changes** record `Applying`, alter the physical table, and record
  `Applied` after refreshing the view and ingestion connections.
- **Reset** drops the views under every owned name and deletes the tables they
  select.

Physical-table deletion is best effort: a failure is logged and leaves the
table behind for manual cleanup without blocking replication. Reset must
successfully drop each logical view before recreating it. ETL deletes only
tables that a view stops selecting during truncate or reset. A table that no
view selects, for example after a truncate interrupted between creating the
new table and replacing the view, is never discovered or deleted
automatically; find such tables by their
`supabase_etl_<pipeline_id>_<table_oid>_` prefix.

If a truncate's view replacement is confirmed to fail, the view still selects
the previous table. ETL does not checkpoint the failed batch: WAL replay must
retry the truncate before applying later row changes. A timeout, lost response,
or process crash can leave the replacement's outcome unknown; wait for the
outstanding job to finish or confirm cancellation before resuming. See
[Query completion and recovery](#query-completion-and-recovery).

Source table renames change only the logical view. The physical table keeps its
name. BigQuery requires streaming to stop before a physical rename and can
require hours before that rename becomes eligible, so ETL does not rename the
streaming physical table. See BigQuery's [table-rename restrictions](https://docs.cloud.google.com/bigquery/docs/managing-tables#limitations_on_renaming_tables).
In case-insensitive datasets, case-only source renames can conflict with the
existing view name. ETL reports the conflict before changing the destination.
See [Table renames](/explanation/schema-changes/#table-renames) for ordering,
permissions, collision handling, and interrupted transitions.

Adding a column follows BigQuery's native behavior: existing rows receive
`NULL` for scalar columns or an empty array for repeated columns. ETL installs
supported defaults for future inserts; it does not backfill historical rows
with PostgreSQL's add-time default. Subsequent replicated row updates carry
the source values, and a full resync rebuilds all rows. See BigQuery's
[column-addition semantics](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/data-definition-language#alter_table_add_column_statement).

### Storage Write connections and retries

ETL uses the default stream, as required by [BigQuery
CDC](https://docs.cloud.google.com/bigquery/docs/change-data-capture#prerequisites).
The client reuses a bounded pool of HTTP/2 connections across append RPCs and
reconnects after recognized stream failures. Every append RPC sends its writer
schema in the first message. Schema changes invalidate cached descriptors and
connections before writes resume, following Google's [schema-update
guidance](https://docs.cloud.google.com/bigquery/docs/write-api-best-practices#handle_schema_updates).

An append retry retains its physical table, encoded rows, and CDC sequence
numbers. Trace IDs are diagnostic identifiers, not idempotency keys: the default
stream can deliver a mutation more than once, and CDC primary keys and sequence
numbers determine the resulting state. ETL checks every response in a split
append batch; a permanent row or request error prevents local propagation
retries from hiding that failure.

### Query completion and recovery

ETL waits for BigQuery DDL to finish before advancing destination metadata.
Query submission, completion polling, result pages, and retries share a
ten-minute deadline. A pending response keeps the original job ID and location.
Each poll requests a ten-second server wait; another incomplete response is
followed by a one-second pause. The server wait is a hint: HTTP latency can
exceed it, and it does not limit the remote job's lifetime.

Transient HTTP failures allow up to 20 retries of the same request. Backoff
starts at one second, doubles to a 32-second cap, and adds up to one second of
jitter within that cap, following [BigQuery's reliability
guidance](https://docs.cloud.google.com/bigquery/docs/reliability-intro#retry_failed_api_requests).

After an ambiguous error while waiting for completion, ETL checks the same job
with `jobs.get`. A new request ID is allowed only for an explicit retryable
failed-job response or a job whose status is `DONE` with a retryable
`errorResult`. Running jobs, successful jobs, and warnings in `status.errors`
do not authorize resubmission. There are at most four replacement jobs; the
shared deadline can stop either retry loop sooner. Permanent SQL, permission,
and configuration errors require correction.

If the deadline expires after a confirmed retryable job failure, ETL retains
that failure for the worker's retry policy. It does not turn a known failure
into an unknown outcome merely because time ran out during backoff.

Once a query completes, failures to retrieve later result pages retry the
page read without resubmitting the query. If those retries fail, ETL stops
instead of executing the completed query again.

A timeout after submission does not cancel the remote job. ETL reports an
unconfirmed outcome after a submission or polling timeout, or exhausted
request retries, and requires manual recovery instead of automatically
replaying DDL. Expiry before a query request is sent remains retryable.
Use the reported request ID, job ID, and location to investigate the outcome
before retrying or resetting the affected table. View changes and metadata
writes are separate operations; after an interrupted transition, inspect both
before deleting any physical table. Storage Write API propagation retries are
separate from these query retries.

### Recovering a pending BigQuery transition

`Creating` and `Applying` metadata block writes for the affected table.
Restarting does not complete them; recover by resetting the table for a fresh
copy.

1. Stop the pipeline. If a BigQuery request timed out, use its reported job ID
   and location to wait for completion or confirm cancellation before reset.
   Stopping ETL does not cancel an already-submitted BigQuery job, and a job
   that completes after reset can recreate an object.
2. Through the application's state-store integration, reset the affected table
   to `TableState::Init` using `StateStore::update_table_state`. Leave its
   destination metadata and schema snapshots intact: they identify the views
   reset must remove. Enable initial copying when the existing source rows must
   be rebuilt.
3. Start the pipeline. Table synchronization drops the views under every owned
   name, including both names of an interrupted rename, and deletes the tables
   they select. It then clears the old copy state, creates a fresh physical
   table and view, and copies from a fresh source snapshot. If reset is
   interrupted, the retained copy phase and metadata let the next start retry.
4. If fresh creation reports that the view name is already occupied, drop that
   object and restart the pipeline.

Do not manually change pending metadata to `Applied` or delete it to bypass the
error. Doing so skips the copy lifecycle and loses the record of which views
reset must remove.

### Table partitioning and clustering

Use `table_options` to select the physical layout for individual source
tables. `table_options`, along with `max_staleness_mins`, is applied only
when a table is created or recreated, never to a table that already exists.
Restarting a pipeline does not modify an existing table, and changing either
setting has no effect until the table is created again. A table is created,
and so picks up the current settings, when it is replicated for the first
time, when its replication state is reset, or when a source truncate makes
ETL create a new physical table.

```yaml
destination:
  big_query:
    # Project, dataset, and authentication fields omitted.
    table_options:
      tables:
        - table_id: 16384
          partition_by:
            kind: time_column
            column: created_at
            granularity: day
          cluster_by:
            - tenant_id
            - event_type
```

`table_id` is the source PostgreSQL table OID, matching the identifiers used by
`table_sync_copy`. Find it in your database using the qualified table name:

```sql
SELECT 'public.events'::regclass::oid AS table_id;
```

Replace `public.events` with the table you want to configure. Because the
configuration follows the source table ID rather than its name, renaming the
source table does not detach its physical-layout settings. The settings also
apply when a truncate replaces the physical table. If a table is dropped and
recreated, PostgreSQL assigns it a new OID, so its configuration must use the
new `table_id`.

`partition_by` and `cluster_by` are independent. Set either one or both in a
table entry: omit `cluster_by` for a partitioned-only table, or omit
`partition_by` for a clustered-only table. To use BigQuery's default
unpartitioned and unclustered layout, omit that table from `tables`. An entry
with neither option is rejected because it has no effect.

Time-column partitioning supports replicated PostgreSQL `date`, `timestamp`,
and `timestamptz` columns with `hour`, `day`, `month`, or `year` granularity;
`date` columns do not support `hour`. Use `kind: integer_range` with `column`,
`start`, `end`, and `interval` for an integer column, or
`kind: ingestion_time` with `granularity` for ingestion-time partitioning.
Clustering accepts one to four ordered, distinct replicated column names.
BigQuery validates whether clustering column types are supported.

`partition_by.column` and each `cluster_by` entry use the source PostgreSQL
column name; ETL applies the same [flexible column
names](#flexible-column-names) mapping to them as it does to the column
itself, so a partitioning or clustering column does not need to be quoted or
otherwise adjusted for the destination.

See the BigQuery documentation for [partition expressions](https://cloud.google.com/bigquery/docs/reference/standard-sql/data-definition-language#partition_expression)
and [clustering column requirements](https://cloud.google.com/bigquery/docs/creating-clustered-tables#clustered_column_requirements).

### Flexible column names

BigQuery's [flexible column
names](https://cloud.google.com/bigquery/docs/schemas#flexible-column-names)
accept spaces, most punctuation, and non-ASCII Unicode characters. ETL passes
any replicated PostgreSQL column name through to BigQuery for table creation,
schema changes, and row writes; a column name is no longer required to be an
ASCII identifier.

BigQuery documents column names as case-insensitive but does not specify the
Unicode case-folding algorithm it uses for identifier resolution. ETL folds
only ASCII letters when mapping a source column name to its destination name,
matching the [destination-name
collision](/explanation/schema-changes/#ordered-schema-plans) behavior used
elsewhere for BigQuery. `Name` and `name` therefore collide locally and are
treated as one destination column, while `Ä` and `ä` remain distinct. If
BigQuery's own case-insensitivity considers such a non-ASCII pair equivalent,
the table DDL is rejected instead of ETL silently merging the two columns.

### Limitations

- Every replicated source table needs a primary key, and all primary-key
  columns must be included in the publication.
- PostgreSQL arrays containing `NULL` elements are not supported.
- BigQuery stores a top-level PostgreSQL `NULL` array as an empty array, so the
  two source values are indistinguishable in the destination.
- Numeric and JSON values follow BigQuery's native domain, rounding, and
  canonicalization behavior. BigQuery may transform or reject values that do
  not map exactly to its types.
- Supported schema changes are applied automatically, but PostgreSQL default
  expressions and backfill behavior are only supported where they map safely
  to BigQuery. See [Schema Changes](/explanation/schema-changes/).
- BigQuery column renames are subject to BigQuery's row-access-policy and
  metadata limitations. Review [BigQuery schema change
  behavior](https://cloud.google.com/bigquery/docs/managing-table-schemas)
  before renaming columns with tags, aspects, or policies.

## ClickHouse

<DestinationStatus status="public-alpha" />

This status applies to the managed service, not local or self-hosted use.

ClickHouse is the local default destination. `cargo x init` starts ClickHouse
on `http://localhost:8123` (`etl` / `etl`), and `cargo x setup replicator`
writes config for that service. It needs no cloud account.

See the [Standalone Replicator](/guides/standalone-replicator/) guide for setup
and the [ClickHouse destination guide](https://github.com/supabase/etl/blob/main/crates/etl-destinations/src/clickhouse/README.md)
for queries, example flags, and upgrades.

ClickHouse supports a current-state layout with `ReplacingMergeTree` and an
append-only event log with `MergeTree`.

`engine` applies only when ETL creates or recreates a table. ClickHouse cannot
change a table's engine, so if the configured `engine` differs from an existing
table, ETL fails the write rather than silently keeping the old layout. Drop
and resynchronize the table, or revert `engine`.

When ETL has no destination metadata for a source table, it creates the
ClickHouse table and, for `ReplacingMergeTree`, its `__current` view. If either
name already exists, ETL fails the table instead of reusing an object it cannot
prove it owns. This happens when a table is re-added to the publication, when
ETL state is reset against the same database, when two pipelines share a
database, or when a resync after a rename would copy into another table's
destination. Drop the conflicting object or use another database.

### Limitations

- The default `ReplacingMergeTree` layout requires a source primary key and
  ClickHouse 23.5 or newer.
- In either engine, publish every primary-key column if the source has a key.
- In either engine, the source primary key must not be `DEFERRABLE`. A
  deferrable key lets one statement move a row into a key before the key's
  previous row moves out, which per-key current state cannot represent. ETL
  fails the table during its initial copy. A schema change that makes an
  existing key deferrable fails instead, and replication of every table stops
  until you resynchronize this one.
- For updates and deletes on tables with a primary key, replica identity must
  be `DEFAULT`, `FULL`, or `USING INDEX` with the same identity columns as the
  primary key. ETL rejects other index identities. With `NOTHING`, Postgres
  rejects published updates and deletes before they reach ETL. A
  primary-key-changing update writes a tombstone for the old key followed by
  the new row.
- `MergeTree` keeps an append-only event log; current state needs a `limit 1 by`
  query over `cdc_lsn` and `cdc_tx_ordinal`.
- A replicated `TRUNCATE` clears the destination table in either engine,
  including `MergeTree` event history.
- A source type change that changes the mapped ClickHouse type, such as
  `integer` to `bigint`, fails the schema change before ETL alters anything, as
  does `timestamp` to `timestamptz`, which shares a ClickHouse type but
  converts existing values through the session time zone. Replication stops
  until you resynchronize the table. Changes that keep the ClickHouse type,
  such as a longer `varchar`, continue without DDL. Every insert names its
  columns and types, so ClickHouse also rejects writes to a column whose type
  changed outside ETL.
- PostgreSQL `timestamp` and `timestamptz` columns, and their arrays, map to
  `DateTime64(6, 'UTC')`. A `timestamp` value reads back as its source
  wall-clock value in any server or session time zone. Tables created by
  earlier ETL versions use `DateTime64(6)` for `timestamp` and fail with a
  column type mismatch; follow the upgrade steps in the ClickHouse destination
  guide.
- ClickHouse `Date32` and `DateTime64` columns support 1900-01-01 through
  2299-12-31. ETL writes dates and timestamps outside that range exactly, and
  ClickHouse stores them, but reads them back clamped to the nearest limit,
  without an error. For example, `1800-06-15` reads back as `1900-01-01`.
  Filters match neither the source value nor the clamped one. Keep replicated
  dates and timestamps inside this range.
- ClickHouse `Array` columns are non-nullable. As with BigQuery, ETL stores a
  top-level PostgreSQL `NULL` array as an empty array, so the two source
  values are indistinguishable in the destination. `NULL` array elements are
  preserved.
- ETL sends any value RowBinary can encode; ClickHouse applies its own
  conversion and rejection rules.
- You may add `MATERIALIZED`, `ALIAS`, or `EPHEMERAL` columns to a table ETL
  created; ETL ignores them when writing. A resynchronization recreates the
  table without them.
- Dotted nested subcolumns can be renamed only within the same parent, matching
  ClickHouse's documented `RENAME COLUMN` limitation.
- Tombstone cleanup and `OPTIMIZE ... FINAL CLEANUP` are operator-managed.
  Follow [ClickHouse's cleanup requirements](https://clickhouse.com/docs/concepts/features/operations/update/replacing-merge-tree#automatic-upserts-of-inserted-rows)
  to avoid resurrecting deleted rows.

## DuckLake

<DestinationStatus status="public-alpha" />

This status applies to the managed service, not local or self-hosted use.

DuckLake writes through DuckDB to a file or PostgreSQL catalog and local or
object storage.

ETL preserves source schema and table spelling when creating DuckLake tables.
Column names use ASCII lowercase. DuckDB resolves identifiers without regard
to ASCII case, so a case-only source rename keeps the same native table and
moves its replay keys to the new source spelling. A pending target epoch
protects relocated replay markers from maintenance until the rename finishes,
including recovery after a process restart.

Distinct native tables must have distinct `<schema>.<table>` replay keys.
Names can contain dots when the combined key remains unambiguous. For example,
`"a.b"."c"` and `"a"."b.c"` cannot be replicated together. ETL rejects setup,
renames, and resets that would share their replay state.

### Limitations

- Data storage URLs currently support `file`, `s3`, and `gs` schemes.
- Deployments must account for the required DuckDB extensions and the catalog,
  storage, and maintenance services they configure.
- Primary-key sorting requires source tables to have a primary key; other
  sorting modes do not add that requirement.
- Table-sorting entries match source schema and table names exactly. Update
  the entry for a renamed source table to retain its configured sorting.
- DuckLake adds streaming columns as nullable. Supported literal defaults are
  stored as metadata; ETL does not emit `DEFAULT(NULL)` when no source default
  exists, although a catalog client may display an omitted default as `NULL`.

## Snowflake

<DestinationStatus status="public-alpha" />

This status applies to the managed service, not local or self-hosted use.

Snowflake uses direct Snowpipe Streaming and key-pair authentication. ETL stores
inserts, updates and deletes as CDC records. For tables meeting the requirements
below, ETL creates a companion view exposing current state. The raw table remains
available as event history.

### Partial updates and materialization

Snowflake supports complete rows and partial updates. With a supported primary
key and `REPLICA IDENTITY DEFAULT`, Postgres can omit unchanged large values
stored using TOAST. ETL records which columns were omitted so a query can carry
forward their last supplied values. With `REPLICA IDENTITY FULL`, ETL writes
complete update rows.

#### Choosing replica identity and a query

Choose based on how much data changes and how often you query current state:

| Source setting | Stored updates | Query choice and trade-off |
| --- | --- | --- |
| `REPLICA IDENTITY DEFAULT` with a supported primary key | Complete rows and partial updates when Postgres omits unchanged TOAST values. | Use the materialization query. Omitting large unchanged values reduces the payload sent to Snowflake, while resolving individual columns requires more query work. |
| `REPLICA IDENTITY FULL` with a stable primary key | Complete update rows, including unchanged values. | For a history of complete insert/update records, use a latest-event-per-key query. It avoids per-column value resolution, at the cost of sending more source data and repeatedly writing unchanged values. The materialization query also works. |

For tables with large values that change infrequently, start with DEFAULT and
the materialization query, subject to the requirements below. If rows are small
or current state is queried frequently, evaluate FULL with latest-event
selection. Measure ingestion and query costs together using representative
history; reduced payload size alone does not establish a lower total bill.
Query cost also depends on [warehouse size and running time](https://docs.snowflake.com/en/user-guide/cost-understanding-compute#virtual-warehouse-credit-usage).

A latest-event-per-key query selects the event with the greatest
`_cdc_sequence_number` for each primary key, then excludes keys whose selected
event is a delete. Use it only when all relevant insert/update history is
complete and the key and history requirements below hold. For mixed or partial
history, use the materialization query: taking just the latest event would treat omitted
values as NULL. Changing replica identity to FULL does not fill in earlier
partial records.

#### Missing values and materialization

Each CDC record includes `_cdc_missing_columns ARRAY`. An omitted value is stored
as a NULL placeholder with its PostgreSQL attribute number (`pg_attribute.attnum`)
in this array. These IDs remain stable across renames; dropping a column does
not make its ID available for reuse within the same table. They are not row
indexes or Snowflake column positions. An explicitly supplied
SQL NULL has no entry; it replaces the previous value. Complete records have an
empty array. Changed large values and initial copy rows must fit the compressed
request limit.

Query the automatically created `<physical_table>_CURRENT` view:

```sql
select * from PUBLIC_ORDERS_CURRENT;
```

This ordinary view runs the materialization query when read. It does not store
results or run a background refresh, and it requires a Snowflake warehouse.
ETL updates its definition after supported schema changes. No PostgreSQL access,
ETL binary, or manual query generation is needed.

For custom SQL, read the column-ID and primary-key mapping entirely in Snowflake:

```sql
select column_name,
       try_parse_json(comment):column_id::integer as column_id,
       try_parse_json(comment):primary_key_position::integer as primary_key_position
from ETL_DB.information_schema.columns
where table_schema = 'PUBLIC'
  and table_name = 'PUBLIC_ORDERS_CURRENT'
  and try_parse_json(comment):column_id is not null
order by ordinal_position;
```

Replace the example database, schema, and view identifiers. Source-column comments
contain JSON with `column_id` and nullable `primary_key_position`. Diagnostic
columns have descriptive comments instead. Use `GET_DDL('VIEW',
'ETL_DB.PUBLIC.PUBLIC_ORDERS_CURRENT')` to inspect the generated SQL. Refresh
customer-owned SQL after DDL; Snowflake column positions cannot replace these IDs.
The Rust `etl_destinations::snowflake::materialization_query` API is also available
as a query-generation helper.

The query carries forward omitted values, preserves explicit NULLs and respects
delete/reinsert boundaries. It returns `_cdc_anchored`,
`_cdc_unresolved_columns`, and `_cdc_last_sequence` alongside source columns.
An unanchored row or unresolved columns indicates incomplete history; these
flags cannot detect arbitrary publication gaps or removed intermediate events.

The materialization query scans retained history for insert/delete boundaries, then resolves
values from each key's latest complete record and later partial updates. This
limits per-column work when complete records are available, but the initial
history scan remains. Retain the stored events; this query does not make history
pruning safe.

#### Requirements for materializing CDC history

- A stable, nondeferrable primary key with every component replicated. Supported
  key types are `smallint`, `integer`, `bigint`, `oid`, `boolean`, `text`,
  `varchar`, PostgreSQL `"char"`, `char(n)`, `name`, `uuid`, `bytea`, `numeric`,
  `date`, `timestamp`, and `timestamptz`. Other key types need separate validation.
- Stable key values and representation. Column renames and drops are supported;
  ETL refreshes the companion view after applying DDL. Regenerate customer-owned
  materialization queries against the updated mapping.
  The materialization query reserves names beginning with `_cdc_`. The writer
  reserves its three physical CDC column names.
- Complete, uninterrupted publication coverage with unchanged actions, column
  lists and membership, and no row filters, including while stopped.
- A coherent initial snapshot and all accepted history from that generation.
  Do not prune, manually edit or combine generations.

Partial updates enforce the supported key structure and reject a delivered key
change. Complete-row ingestion accepts a broader set of source schemas and
schema changes. Successfully storing an event does not establish that its
history meets the requirements for materializing CDC history. Publication changes are an
operator responsibility; ETL cannot detect events Postgres never emits.

pgoutput announces a changed relation with the next row event; DDL alone does
not update the destination or its view.

Omission metadata keeps its meaning after a rename or drop, including renaming
a key without changing its value. `_cdc_unresolved_columns` reports current
column names. Dropping and re-adding a name creates a new column with a new ID.
Added columns retain the destination's existing default-value limitations: only
supported literal defaults populate historical records. This feature does not
add support for arbitrary defaults or type changes. See
[Schema changes](/explanation/schema-changes) for the existing DDL behavior.

After incompatible key/schema/publication changes or lost history, request a
full resync through the supported reset operation: recreate the owned destination
history from a new coherent snapshot. Recreate the pipeline if per-table resync
is unavailable. Standalone deployments without reset support should use fresh
ETL state and a fresh destination schema. A normal restart does not request a
resync; manual truncation is not a substitute.

### Companion-view permissions and lifecycle

The ETL role needs `CREATE VIEW` on the destination schema and ownership of its
raw tables and views. For example:

```sql
grant create view on schema ETL_DB.PUBLIC to role ETL_ROLE;
```

Grant this before starting or upgrading the replicator. ETL does not change role
grants automatically. Missing permissions or conflicting objects fail setup or
startup reconciliation. Consumers need `SELECT` on the view and the usual
usage privileges for its database, schema, and query warehouse.

ETL owns the `_CURRENT` and `_CURRENT_PENDING` companion names and their comments.
For physical names longer than 239 characters, the view name is
`_ETL_<uppercase SHA-256 of the physical name>_CURRENT`; its recovery name adds
`_PENDING`.
The second name is an internal recovery object, not a supported query interface.
Before a drop or rename, the public view becomes temporarily unavailable; it is
restored after the raw schema and new definition are ready. Add-only changes
replace the definition without taking the public name offline. Startup restores
existing ETL-owned public or pending views for tables that completed initial
synchronization, including idle tables. Tables without an owned view wait for
initial copy or a source relation to establish eligibility before ETL creates
their first view. Stored destination schemas do not retain replica identity;
primary-key columns alone are insufficient. This applies to legacy tables and
manually removed views too. Tables awaiting a fresh copy and errored tables are
skipped. Interrupted raw DDL follows the existing schema recovery/resync
requirements.

Explicit view grants survive definition replacement and same-name resync.
Do not attach custom policies, tags, or streams to ETL-owned views or change
their definitions/comments. Create a separate customer-owned view for custom
behavior. Replacing an ETL view makes streams on it stale. During initial copy
or resync, the view may expose a snapshot that is still being copied.

Complete-row ingestion for keyless tables, unsupported identities/key types, or
source names beginning with `_cdc_` remains raw-only and emits a warning. Losing
eligibility after a view has been created makes it unavailable and fails
reconciliation before changing the applied raw schema. A restart can restore
the view against that previous schema; the next source relation rejects the
unsupported transition again. Fresh pipeline state requires an unused
destination namespace or deliberate cleanup of old tables and both reserved
companion names.

### Source table renames

ETL renames the downstream table when a source table is renamed within the
same PostgreSQL schema. It drains pending writes, retires the old streaming
channel before freeing its table name, renames the table, applies
column changes, and reopens ingestion at the previous committed offset. The
new snapshot is marked applied only after these steps succeed. Renames fail
before any change when a table or view occupies the mapped target name. The
old companion view is retired and a new one is created for the resulting raw
table name. Explicit grants on that new view must be recreated. A case-only
rename keeps the mapped raw and companion names. Moving the source table to
another schema is unsupported.

The destination role needs `OWNERSHIP` on the table and `CREATE TABLE` on its
schema to rename it. See [Snowflake's rename requirements](https://docs.snowflake.com/en/sql-reference/sql/alter-table#parameters).

See [Table renames](/explanation/schema-changes/#table-renames) for destination
behavior and recovery after an interrupted transition.

### Limitations

- Setup requires a Snowflake user and role with the documented warehouse,
  database, and schema privileges.
- The effective `QUOTED_IDENTIFIERS_IGNORE_CASE` parameter must be `FALSE`.
  Connectivity validation rejects other settings because ETL preserves quoted
  source column names exactly. See [Snowflake identifier
  resolution](https://docs.snowflake.com/en/sql-reference/identifiers-syntax#controlling-case-using-the-quoted-identifiers-ignore-case-parameter).
- Schema evolution support is still in progress. Only defaults that ETL can
  translate safely at table creation or column addition are applied. Later
  existing-column default changes are skipped because Snowflake default
  provenance cannot be inferred safely.
- `json` and `jsonb` use native `VARIANT` storage and preserve SQL `NULL`
  separately from JSON `null`. ETL omits destination defaults for these columns
  and removes existing defaults before opening or refreshing their streaming
  channels. PostgreSQL still applies source defaults before replication. If a
  destination default cannot be removed, channel setup fails before writing.
  Existing destination columns mapped from `json` or `jsonb` must have physical
  type `VARIANT`; incompatible types are rejected during channel setup.
- PostgreSQL `json[]` and `jsonb[]` arrays containing SQL `NULL` elements are
  rejected during encoding because the ingestion format cannot distinguish
  them from JSON `null` elements. JSON `null` elements, empty arrays, and a
  whole SQL `NULL` array are supported.
- Earlier versions could merge SQL `NULL` and JSON `null`. The encoding fix
  does not repair existing rows; restoring that distinction requires the
  source data or a fresh copy.
- Validate channel recovery, committed offsets, and account-specific resource
  limits before production use.

### Existing destination tables

For ETL-owned tables using the supported previous CDC format, ETL validates the
column set and CDC metadata, adds the nullable `_cdc_missing_columns` ARRAY
column, and validates the result before opening the write channel. Existing
insert/update records have NULL metadata, interpreted as complete within their
replicated schema at event time. Historical deletes remain deletion boundaries.
The upgrade preserves stored history and replication offsets and requires no
backfill.

The configured Snowflake role must allow the ALTER. Unexpected schemas and
metadata types remain errors. Customer-owned queries must support partial
records before consuming them; automatic table upgrades do not update those
queries. The materialization query requires `_cdc_missing_columns` to exist.

## Iceberg

<DestinationStatus status="deprecated" />

The Apache Iceberg implementation is retained for compatibility and is not
recommended for new deployments.

### Limitations

- Schema-change DDL is not supported. A newer relation schema is rejected even
  when only a default, nullability, mapped-equivalent type, or publication mask
  changed. Existing tables must match the exact generated Iceberg schema.
- Initial setup reuses an existing table when its schema matches. Use a
  namespace reserved for ETL because subsequent writes and resets treat that
  table as owned.
- Apache Iceberg supports native schema evolution, but this deprecated ETL
  adapter does not implement it and does not translate PostgreSQL defaults.
- The destination is deprecated and is not receiving the same product
  investment as the active destination implementations.

## Custom destinations and upstream support

Adding an official destination is a long-term maintenance commitment. It
requires durable and idempotent writes, schema-evolution behavior, restart and
recovery coverage, integration infrastructure, credential handling, ongoing
dependency updates, and operational support. For that reason, maintainers are
careful about accepting new destination implementations upstream. Open an issue
or discussion before investing in an upstream implementation; acceptance is
not guaranteed.

You do not need to contribute a destination upstream to use ETL. Implement the
[`Destination`](/explanation/traits/#destination) trait in your own Rust
project, wire it into `Pipeline::new`, and maintain it alongside your
application. See [Custom Implementations](/guides/custom-implementations/) for
a complete example.
